# StudyBuddy UI audit and responsive stabilization — 2026-09-15

## Scope and method

This audit covered the Next.js App Router shell, route guards, shared UI primitives, dashboard glass components, schedule/timer interactions, query-driven list screens, and the existing Go/Fiber API boundary. Existing APIs, cookie authentication, same-origin `/api` proxying, routing, business logic, MongoDB/Redis behavior, and prior scheduling/call-tracking changes were preserved.

Source inspection covered 27 view/route surfaces: Landing, Auth, ResetPassword, Onboarding, Dashboard, Tasks, Goals, Show Up, Schedule, Reports, Journal, Mentor, Achievements, Notes, Leaderboard, News, Notices, Friends, Messages, Help, Settings, Admin, Support, Contact, About, Privacy, and Terms. Shared inspection covered Layout, Button, Dialog, GlassModal, LoadingScreen, OfflineIndicator, timer/clock, ScheduleTimeline, availability, cards, inputs, selects, dropdowns, toast, and loading/error states.

Playwright MCP was used for rendered checks. The local backend was not started, so public routes were rendered directly and the protected Schedule route was rendered with local-only mocked `/api` responses; no project code, secrets, or user data were sent anywhere.

## Remaining issues and release recommendation

### 1. Real authenticated browser/API verification

- **Impact:** Production cookie authentication, backend connectivity, realtime polling, and data-populated dashboard screens were not exercised in this local run.
- **Location:** Protected routes and `/api` proxy/backend deployment.
- **Reason it remains:** The local backend/database was unavailable; the browser smoke used safe local mocks.
- **Next step:** Run the same protected route matrix against a staging environment with a test account, then verify login/logout, schedule generation, todo mutations, dialogs, and realtime invalidation in a real browser.

### 2. No committed Playwright suite

- **Impact:** Browser checks are repeatable MCP evidence but not yet CI-enforced Playwright tests.
- **Location:** Repository has no Playwright config/package.
- **Reason it remains:** Installing a new browser dependency was intentionally avoided during this stabilization pass.
- **Next step:** Add a pinned Playwright dependency and CI project only after deciding the supported staging/auth fixture strategy.

### 3. Production-like network and auth browser verification

- **Impact:** Production cookie authentication, backend connectivity, realtime polling, and data-populated screens were not exercised in this local run.
- **Location:** Protected routes and `/api` proxy/backend deployment.
- **Reason it remains:** The local backend/database was unavailable; the browser smoke used safe local mocks.
- **Next step:** Run the same protected route matrix against a staging environment with a test account, then verify login/logout, schedule generation, todo mutations, dialogs, and realtime invalidation in a real browser.

### Recommendation

**NOT READY for an unconditional production release yet.** No known P0 remains, the addressed P1/P2 fixes pass local static/build/browser checks, and the backend/API contracts remain intact. A staging authenticated-browser pass is required before declaring release readiness; the residual Friends/Leaderboard failure-state work is recommended before a final UI sign-off.
